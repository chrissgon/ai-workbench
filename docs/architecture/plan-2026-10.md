# Plan: from the review of 2026-10-01 to every skill evaluated once

Built on `docs/architecture/review-2026-10-01.md`; D-numbers refer to its decision table. Status: **draft**, valid once the maintainer decides D1 to D6. A phase starts only when the one before it is done, except where it says "parallel". Every phase ends in a pull request; no skill is measured before phase 4.

The aim that orders everything: **the 48 skills are measured one more time, in an environment that will not change under them.** So everything that changes what a record means comes first, and everything else is kept out of the way of that.

## Phase 0. Save the state (done 2026-10-01)

- Backlog T11 carries the state (26 `evaluated`, 22 `draft`, which records were not updated and why, known case defects); T16 and S19 carry the environment problem; `docs/decisions.md` carries the pause.
- The branch with the 26 records and the repaired cases is merged as it is. Its records were measured on the host, before the environment existed; phase 4 replaces every one of them.

## Phase 1. Decide (maintainer)

- D1 to D6 (environment, runner location, record and staleness, gate rule, authentication, network). D5 and part of D4 and D6 are confirmed by the proof of concept in phase 3; the rest is decided now.
- D7 to D14 can be decided now or when their phase comes; they do not block the evals.
- Each decision is written in `docs/decisions.md`.

## Phase 2. Structure that costs no model call

In this order; each is a small pull request with its tests.

1. **Move the eval runner out of the skill (D2).** New top-level `evals/`: runner, grading template, gate configuration, tests. Update `AGENTS.md` (layout, the adapter contract), `core-skill-creator`, the secret registry, `.gitignore`, the hook and CI. `core-skill-creator`'s hash changes one last time for this reason.
2. **Record and staleness (D3).** New record fields (environment, runner and CLI versions, grader, measurement version); `eval_status.py` compares strong model, grader and measurement version; records made before read `stale`. Tests for each cause of `stale`.
3. **Gate rule (D4).** Tolerance and grader named in the gate configuration; `gate()` and its tests.
4. **Checks that run (D10, part).** The hook and CI discover test folders; `--check-cases` joins `validate.py`; fix the iteration race and the README contradiction on parallel runs.
5. **Backlog hygiene (D14).** Duplicate id, built items ticked, T6 folded into T16.

Parallel with 1 to 5, since they touch other files: D13 (Python version rule and CI job).

## Phase 3. Proof of concept of the container (one skill, both tiers)

Goal: remove the unknowns before building. One skill with a script and no browser, then one with a browser.

- An image with pinned runtimes, git, package tools, a browser and the two runner CLIs.
- One run per container: the run folder mounted, nothing else.
- Strong-tier authentication with a token (D5); floor tier with its provider key.
- Egress limited to the provider (D6); one `allow_web` case with open egress.
- Does the strong runner's own sandbox start inside the container, or is the container the only boundary (a third adapter mode: allow every command)?
- Stopping: a stopped runner stops its container.
- Measure: start-up time per run, scores against the host records of the same skill, runs in parallel.

Exit: a short report in `docs/architecture/` with what worked, what did not, and the final D1, D5 and D6. If the container cannot carry the strong tier, the fallback is the host with the sandbox for both tiers (S19 done on the host) and the record says `host`.

## Phase 4. Build the environment and measure once

1. **Executor layer (D1).** Host and container executors behind one interface, used for model runs, setup, the git fixture commit and grading. The adapters lose their home, keychain and process-group code where the container makes it dead; their shared parts move to one helper.
2. **Image as a versioned artifact.** Its definition in `evals/`, built by a script, its digest written into each record. Raising the measurement version is part of changing the image.
3. **Cases adapted.** Stand-ins for cases tied to one operating system; dependencies a case installs come from the image; the known case defects from T11 (a research skill's cases without `allow_web`, two assertions that never fail, a fixture builder missing from the repository).
4. **Measure the 48**, five at a time, full runs. Repair what fails under the rules already agreed (the skill is fixed when the output is not good; an assertion is changed only when it never influences the score or fails a good run for a formality; every change listed before and after).
5. **T11 closes** when no skill is `draft` or `stale`. T12's local-model measurement runs in the same environment afterwards and writes no record.

## Phase 5. Core structure (parallel with phase 4, different files)

Changes inside a skill folder make that skill `stale`, so these are batched **before a skill's phase-4 run**, never after it.

1. **Tests into the skills (D10).** Split the shared test file per skill, add tests for the 11 untested scripts.
2. **Shared code (D8).** One source, a sync script, one identity test; reconcile the diverged pair; a common Markdown-parsing helper for the lint scripts as they are next touched.
3. **Providers by class (D9).** One resolution function; the skills that name an implementation name the class; the workbench-root variable; the installer copies what skills need.
4. **Artifact contract (D7).** Placeholder syntax, `updates` beside `outputs`, dangling inputs as errors, the project layout checked against declarations.
5. **Validation rules.** Required keys, vocabularies, cited skill names, packs scanned, one YAML loader.
6. **Flows (D12).** Citations removed or marked planned; "run X" rewritten.

## Phase 6. Later rounds, each with its own plan

- Runtime (D11): generic runtime in its own folder, provider selection, ledgers out of the cache folder, the Linux scheduler on a real host, T15.
- T14: open backlog items move to the issue tracker, after phase 2.5 and when T12 closes.
- Documentation drift listed in the review.

## Risks

| Risk | Handling |
|------|----------|
| The strong runner cannot authenticate or run in a container | Phase 3 finds out on one skill; fallback is the host with both tiers sandboxed |
| Egress filtering breaks the runner's own calls | Proof of concept lists the hosts each runner needs before the rule is written |
| Scores move between host and container | Expected; the record names the environment and every skill is measured in the same one |
| Phase 5 changes stale a skill just measured | Phase 5 items land before that skill's run; the order of the phase-4 batches follows phase 5's progress |
| The model account's limit | Five skills at a time; the measurement is spread over days |
