# Architecture review, 2026-10-01

Why this exists: in one day the eval harness changed four times for causes found while measuring, and each change altered what the recorded results mean (`docs/decisions.md`, "Skill evaluation pauses for an architecture review"). Before an isolated eval environment is built (backlog T16), the whole repository was reviewed, tests included, to decide the target once and plan the changes from it.

How it was made: three read-only reviews run in parallel on the main branch (evals and tests; core and validation; providers, runtime and backlog), each citing files and lines, consolidated here. Nothing was run against a model. Items marked *not verified* were not checked. The plan built on this review is `docs/architecture/plan-2026-10.md`.

Status of the decisions below: D1, D2, D3, D5 and D6 were **decided** by the maintainer on 2026-10-01 (`docs/decisions.md`), D1 with a change: there is no host mode. D4 was decided the same day (both models at the threshold, and the skill must not lower the strong model beyond a tolerance). D7 to D14 are **proposed**: each has a recommendation and none is decided until the maintainer says so.

## What holds up

- The layers are the right ones: a harness-neutral core, adapters that read it, providers behind requirement classes, contracts for what a project holds. Frontmatter is uniform across the 48 skills, no `SKILL.md` is near the size limit, agents are clean.
- Quality is a computed record, not a tick (`evals/result.json`, `scripts/eval_status.py`).
- Providers share conventions: exit codes, `--check`, pinned dependencies, offline tests per class.
- An eval run is already a self-contained unit: one folder outside the repository holding the case, the output and the prompt. That is what makes an isolated environment a contained change.

## Findings

### A. Evals: results depend on the machine and the record does not say how it was measured

1. **Host dependence.** `PATH`, `HOME` and `SHELL` pass into every run, so the host's git, language runtimes and package tools decide results; case setup runs on the host; a shell profile can change what a plain `cd` does; runner versions exist only in comments; two code paths are for one operating system (a keychain, a per-user temporary folder).
2. **The two tiers do not have the same rights.** The strong tier runs in a sandbox but with the person's home, and the case's `allow_commands` and the skill's scripts run outside the sandbox; the floor tier is unconfined and ignores `--allow-command` and the spend limit (backlog S19). A floor run finds the workbench by searching the disk.
3. **The record does not capture the measurement.** It has no environment, runner version, sandbox mode, grader or grading-template version. Only a floor-model change makes a record `stale`: a change of strong model, grader, adapter or runner does not. Records made on the previous strong model still read `evaluated`.
4. **The eval runner lives inside a skill.** `skills/core-skill-creator/scripts/eval_run.py` (1,342 lines) is shared infrastructure: 19 of the 23 commits that touched that skill touched the runner, each changing the skill's hash; the grading template that grades every skill is in the same folder; the runner reads `adapters/` and `scripts/`, which a core file should not (principle 2).
5. **Gate gaps.** "Strong with the skill at least as good as without" has no noise margin although the spread is computed; the grader is the strong model, so it grades its own runs; contamination is checked only on without-skill runs and only for the running checkout's path.
6. **Flakiness.** Two runs of the same skill race for the iteration number; change detection is by modification time; the early-end check matches English phrases; one README says runs must be one at a time and the runner says parallel is safe.
7. **Checks that do not run.** The pre-commit hook runs tests only for `providers/` and `scripts/`, so a commit touching the runner, an adapter or a skill's script runs none locally; CI lists test folders by hand, so a new one is skipped silently; `eval_run.py --check-cases` needs no model and is in neither; the real runner CLIs and the sandbox are never exercised in CI.
8. **Adapter duplication.** Installing the skill, copying `shared/`, argument parsing and the stop logic are near-identical in the two eval adapters.
9. **Overlap in the backlog.** T6 (an optional container runner through an existing framework), T16 (a fixed environment) and S19 (confine the floor tier) are one piece of work.

### B. Core: the artifact contract and the shared code

1. **The artifact graph is declared but not usable.** 14 of 38 output paths carry placeholders matched as plain strings; 7 outputs have several producers (one has 10, the state file has 6) against "one artifact per capability"; 16 skills read and write the same path, so the graph is two cycles and gives no order; 2 inputs have no producer; 9 outputs have no reader; 8 output paths are missing from `contracts/project-layout.md`.
2. **`scripts/validate.py` enforces less than `AGENTS.md` says.** A dangling input is a warning; `packs/` is not scanned as core; nothing checks the required metadata keys, `requires` against the known classes, the `side_effects` vocabulary, the token limit, the two-case minimum, skill names cited by agents and flows, or pack patterns; the YAML loader differs by machine (a library when installed, a subset parser otherwise).
3. **Flows are cited and not built.** Three flows named in the orchestrator, a contract and the area map do not exist; 38 of 47 capabilities are in no flow, so sequencing lives in prose, and at least three capabilities say "run X", which drifts from "artifacts over invocation".
4. **Skills depend on files outside their folder with no mechanism.** Three skills call `<workbench>/providers/...` through an unresolved placeholder; two name a concrete provider (one of them an implementation for a single operating system) where their `requires` names the class; one installer mode copies neither `shared/` nor `providers/`; a provider change never marks a dependent skill `stale`.
5. **Duplicated scripts.** Two scripts are byte-identical in two skills and one in three places, held together by tests that assert the copies match; another pair has diverged (122 differing lines, one copy tested); 19 lint and check scripts (2,552 lines) each parse Markdown their own way; one fixture exists in 9 folders with small differences.
6. **No single test convention for skill scripts.** One 1,604-line file holds most tests, five per-skill files sit beside it, one skill keeps its tests in its folder; 11 of 53 scripts have no test; script CLIs diverge (22 use a parser library, about 14 offer `--json`, 11 are executable).
7. **Documentation drift.** Shared references that are listed and do not exist; templates described in one place and living in another; `requires` classes named with and without a prefix; files under `scripts/` that the layout in `AGENTS.md` does not list.

### C. Providers and runtime

1. **The runtime bypasses provider selection and is one agent's script.** It builds provider paths itself, hardcodes one store and one scheduler implementation, and its task text and categories are one use case, while `contracts/runtime.md` describes a generic runtime. The next runtime items would be a rewrite, not an extension.
2. **Python version.** The scheduled tick runs on the system interpreter (3.9) while one provider it starts declares 3.10 or later; the guard is a syntax test and CI runs one version only.
3. **Idempotency ledgers live in a cache folder.** Clearing the cache, or a fresh container, loses the "already published" record and allows a duplicate.
4. **Two scheduler implementations share 43 same-named functions** kept identical by hand; one has never run on a real host.
5. **Store concurrency (T15)** is open on an unconfirmed hypothesis, and concurrent `init` is a normal path of the runtime.
6. **Backlog as a source of truth.** Two items share the id T8; the runtime items R1 to R7 are unticked although built for one agent; several items wait only on a real run; done items carry long histories. This has to be clean before T14 moves open items to the issue tracker.

## Decisions to take

Each has a recommendation. D1 to D6 fix what a record means: they are decided before any skill is measured again. D7 to D12 are structural and independent of the evals. D13 and D14 are housekeeping.

| # | Decision | Recommendation |
|---|----------|----------------|
| D1 | Where eval runs execute | A container per run, from one pinned image, started by a new **executor layer** between the runner and the adapters (the runner plans, the executor decides host or container, the adapter drives one CLI). The container is the sandbox for both tiers: same rights, nothing of the workbench or the person's home mounted. **Decided with a change: evals run only in the container; there is no host mode, so that there is one standard.** This closes S19 and replaces T6. |
| D2 | Where the eval runner lives | Out of the skill: a top-level `evals/` folder (runner, executor, grading template, tests, gate configuration), allowed to read `adapters/`. `core-skill-creator` keeps the procedure and points at it. |
| D3 | What a record captures and what makes it stale | The record names the environment (the image digest), runner and CLI versions, strong model, grader and a **measurement version**: a number in the gate configuration, raised on purpose when a change alters what is measured. `stale` when the skill folder, the floor model, the strong model, the grader or the measurement version differs. Hashing the runner itself is rejected: every refactor would stale 48 skills. |
| D4 | The gate's rule | Keep the two conditions; add a noise margin to the strong comparison (with the skill at least the baseline minus a fixed tolerance, decided from the measured spread); name the grader in the gate configuration. A grader different from the model under test is weighed in the proof of concept (cost against bias). |
| D5 | How the strong runner authenticates in a container | A long-lived token passed as an environment variable through the secret store, never the keychain. *Not verified*; the proof of concept settles it. |
| D6 | Network policy inside the container | Egress only to the model provider, through an allowlisting proxy; an `allow_web` case gets open egress; language dependencies and a browser are baked into the image; a case that installs packages uses what the image holds. Cases tied to one operating system get a stand-in. |
| D7 | The artifact contract | Define the placeholder syntax; split `outputs` (one owner) from `updates` (shared ledgers such as the state file, a plan, a calendar); then a dangling input is an error and `contracts/project-layout.md` is generated or checked against the declarations. |
| D8 | Code shared by several skills | Vendored copies generated by one sync script from a single source, with one generic identity test. A skill stays self-contained and installable alone; a shared library would break that. |
| D9 | How a skill reaches a provider | One resolution function (class to script, from the environment), used by the runtime and the doctor; skills name the class and the variable, never an implementation; the workbench root comes from one documented variable. |
| D10 | Where tests of skill scripts live | In the skill: `skills/<name>/scripts/tests/`. The hook and CI discover test folders instead of listing them, and run `--check-cases`. |
| D11 | What the runtime is | Decide generic or one agent's script before the next runtime item. Recommended: generic, in a top-level `runtime/` folder, with the per-agent parts behind a handler. Not needed for the evals; it can wait for its own round. |
| D12 | Flows cited and not built | Remove the citations, or mark each as planned with a backlog id; rewrite "run X" in capabilities as "needs artifact Y". |
| D13 | Python versions | A rule in `providers/CONTRACT.md`: which scripts must run on the system interpreter, with CI running them on that version. |
| D14 | Backlog hygiene before T14 | Fix the duplicate id, tick what is built, cut done items down to one line with a link to the decision. |

## What this does not cover

The content quality of each skill (the evals measure that), the harness installers end to end, and anything marked *not verified* above.
