# PB8 research: always-on, low-cost hosting for the agent runtime

Research notes, 2026-09-30. Every price comes from the vendor's own page or price feed, accessed 2026-09-30 (sources at the end, numbered [S1]...). "Not found" means I looked and the page did not say. Anything not from a source is marked **Assumption**. USD unless stated; EUR prices are Hetzner's, excluding VAT.

## 0. What has to move (from the repository, read 2026-09-30)

| Piece today (Mac) | File | What it needs from a host |
|---|---|---|
| Trigger: launchd `StartInterval` every N min, snapshot + hash of the approved command, `run.lock`, `timeout_minutes` | `providers/scheduler/launchd.py` | a scheduler (every 10 min + 3 fixed times/week), no overlap, bounded run time |
| Runtime tick: mailbox -> events -> claim -> agent -> gate -> publisher or inbox | `scripts/runtime.py` (stdlib only; uses `subprocess`, `fcntl`, `tempfile`) | Python 3, subprocesses, a writable temp dir |

| Agent run: `claude -p` with `--tools Read,Glob,Grep`, skills copied into a fresh cwd, `--max-budget-usd` | `adapters/claude-code/run-agent.sh` | the Claude Code binary + credentials, or a different adapter |

| Publisher: LinkedIn Posts/Comments API, 60-day token, no refresh; idempotency **ledger file** under a file lock | `providers/publisher/linkedin.py` | outbound HTTPS, 1 secret (+ expiry), a persistent ledger |
| Project files: policy (gate binds to its hash), voice, brand files, `state.md` approvals, `engagement-log.jsonl` | project `docs/` | read access at run time; the log is written |
| Secrets resolver: env var first, then OS keyring | `providers/secrets/resolver.py` | env vars on a server (keyring usually absent on a headless box) |
| Person's side: `runtime.py inbox/approve/reject`; macOS notifications | `runtime.py`, `launchd.py` | wherever the store lives, the person must be able to run `approve`; a notification channel that is not macOS |

Workload used below (from the task): ticks every 10 min = 6 x 24 x 31 = **4,464/month** (31-day month; 4,320 in 30 days), a few seconds each; **0-900 LLM runs/month** (0-30 comments/day); **12 posts/month**.

**Assumptions used in every estimate** (label them if reused):
- A1: a tick without comments takes ~3 s of compute; ~10 s where a container must start (Cloud Run).
- A2: an LLM run through a direct API call waits ~30 s wall time; through the Claude Code CLI (multi-turn, reading tools) ~90 s.
- A3: a month has 730 hours (for hourly-priced servers).
- A4: storage (SQLite file, logs) stays under 1 GB.

## 1. The LLM call (applies to every option)

### 1.1 Can the Claude Code CLI run headless on a server on a personal subscription?

**Technically yes.** Claude Code's authentication page [S30]: `claude setup-token` generates "a one-year OAuth token" for "CI pipelines, scripts, or other environments where interactive browser login isn't available"; set it as `CLAUDE_CODE_OAUTH_TOKEN`. "This token authenticates with your Claude subscription and requires a Pro, Max, Team, or Enterprise plan. It can only make model requests." Precedence: `ANTHROPIC_API_KEY` (3rd) outranks `CLAUDE_CODE_OAUTH_TOKEN` (5th); in `-p` mode an API key present is always used. `--bare` mode "does not read `CLAUDE_CODE_OAUTH_TOKEN`" and "never reads OAuth credentials" [S30][S31]; the headless page says `--bare` "is the recommended mode for scripted and SDK calls, and will become the default for `-p` in a future release" [S31]. So a future default change could break subscription auth in `-p` unless the adapter avoids `--bare`. On Linux credentials live in `~/.claude/.credentials.json` (0600) [S30].

**Terms: a grey area, to put to the operator, not to decide.**
- Consumer Terms (Free/Pro/Max; effective 2025-10-08), section 3 item 7, forbids: "Except when you are accessing our Services via an Anthropic API Key or where we otherwise explicitly permit it, to access the Services through automated or non-human means, whether through a bot, script, or otherwise." [S32]
- Claude Code legal page: "OAuth authentication is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications." "Advertised usage limits for Pro and Max plans assume ordinary, individual usage of Claude Code and the Agent SDK." Developers building products "should use API key authentication". [S33]
- Against that, Anthropic's own docs document `setup-token` for "CI pipelines, scripts" [S30], which reads as an explicit permission for running the unmodified binary in automation for yourself.
- Reading: running the unmodified `claude` binary on your own server, for yourself, with `setup-token` is documented; a bot that replies to strangers every 10 minutes is closer to "automated or non-human means". **Not resolved by the sources.** The clean path for a server is an API key (Console) or OpenRouter. The repository already records "Claude models run with the maintainer's own login" for evals (contracts/secrets.md); whether that extends to an unattended server is the operator's decision (AGENTS.md principle 5).

**Hardware:** Claude Code's system requirements are "4 GB+ RAM, x64 or ARM64 processor"; Ubuntu 20.04+, Debian 10+, Alpine 3.19+ [S34]. This rules out the 512 MB-1 GB instances below *for the CLI path*. It does not affect a direct API call.

**Alternative Anthropic-hosted scheduler, checked and rejected:** Claude Code routines (research preview) run on Anthropic's cloud on the subscription, but "The minimum interval is one hour", runs have a daily cap per account, and a routine runs "autonomously as full Claude Code cloud sessions: there is no permission-mode picker, and the session runs shell commands" [S35]. That breaks both the 10-minute tick and the runtime's rule that the model has reading tools only (contracts/runtime.md).

### 1.3 Cost per reply (15,000 input + 400 output tokens, one API call)

Sonnet 5.5
- No caching: 15,000 x $2/1e6 = $0.0300; 400 x $10/1e6 = $0.0040 -> **$0.0340**
- Cache cold, 5-min write: 15,000 x $2.50/1e6 = $0.0375 + $0.0040 -> **$0.0415** (worse than no caching)
- Cache warm (hit on all 15k): 15,000 x $0.20/1e6 = $0.0030 + $0.0040 -> **$0.0070**
- 1-h cache, ~2 replies/hour (30/day over ~16 h, **Assumption**): write 15,000 x $4/1e6 = $0.060 + $0.004 = $0.064; hit $0.007; average (0.064 + 0.007)/2 = **$0.0355**

Haiku 4.5
- No caching: 15,000 x $1/1e6 = $0.0150 + 400 x $5/1e6 = $0.0020 -> **$0.0170**
- Cold 5-min write: 15,000 x $1.25/1e6 = $0.01875 + $0.0020 -> **$0.0208**
- Warm hit: 15,000 x $0.10/1e6 = $0.0015 + $0.0020 -> **$0.0035**

DeepSeek V3.2 (OpenRouter default listing)
- No caching: 15,000 x $0.28/1e6 = $0.0042 + 400 x $0.42/1e6 = $0.000168 -> **$0.0044**
- Cache hit: 15,000 x $0.028/1e6 = $0.00042 + $0.000168 -> **$0.0006** (no cache-write price listed)

**Does caching help at this volume?** The 5-min cache only hits when two comments are handled within 5 minutes, i.e. inside the same tick (the tick is every 10 min, so a cache written in one tick has expired by the next). With 0-30 comments/day, most ticks with work handle one comment: expected cost is near the uncached figure, and slightly above it with 5-min writes. The 1-h cache breaks even at about 2 replies/hour. Caching matters only if replies are batched (for example, handle all of a tick's comments back to back with an identical prefix).

**The CLI path costs more than one call.** Through `claude -p` with reading tools, the model reads files through several tool turns and Claude Code adds its own system prompt and tool definitions; each turn resends the context (Claude Code caches automatically, **Assumption** based on the tool-turn design; not verified here). Real per-reply cost on the CLI path is **unknown**: measure it from `timing.json` (`cost_usd`) during the planned rehearsal. A direct-API adapter that puts the skill and brand files in one stable prefix (no tools) is the path whose cost the table above describes.

## 2. AWS

### 2a. Lambda + EventBridge Scheduler (serverless)

**Mapping**
- Scheduler: EventBridge Scheduler `rate(10 minutes)` for the tick; three `cron(...)` schedules (or one with a day-of-week list) for posts, evaluated in an IANA time zone, 60-second precision [S5]. Overlap: set the tick function's reserved concurrency to 1 (**Assumption**: standard Lambda setting; it replaces `run.lock`).
- Compute: one Python Lambda (arm64). Max timeout 900 s; memory 128-10,240 MB; `/tmp` 512-10,240 MB [S4]. The tick fits; an LLM run through the CLI (timeout_seconds 600 in runtime.json) fits under 900 s but leaves little margin for several comments per tick.
- LLM: **direct API adapter recommended** (stdlib `urllib` call to the Messages API or OpenRouter from inside the function). The CLI path means a container image with the `claude` binary, 4 GB memory per [S34], `HOME` pointed at `/tmp`, and the subscription/API-key question.
- State, two options:
  - **DynamoDB** (on-demand): a new `providers/store/dynamodb.py` behind the same CLI verbs. Claims and "one action per key" map to conditional writes (**Assumption**: DynamoDB `ConditionExpression`, standard feature, not re-verified today). Most work, cleanest concurrency. The Mac can run `runtime.py approve` against the same table with AWS credentials.
  - **SQLite file in S3**: download at start of tick, upload at end with `If-Match: <ETag>`; a concurrent writer gets `412 Precondition Failed` [S13]. Keeps `sqlite.py` unchanged; requires single-writer discipline (reserved concurrency 1, and the person's `approve` from the Mac using the same conditional upload). Do **not** put SQLite on EFS: SQLite's own page says locks "have been known to operate incorrectly for some network filesystems" and a network fault can leave "the remote database ... corrupted" [S12].
  - The publisher's ledger file (`linkedin.py`) and `engagement-log.jsonl` must move to the same place (store table or S3 object), or they are lost with each container.
- Project files: bundled into the deployment package or read from S3 at each tick (the gate hashes the policy file; the bundle's hash becomes part of what was approved).
- Secrets: SSM Parameter Store SecureString (standard) or Secrets Manager, read by the function's IAM role and exported as env vars for `resolver.py`.

**Monthly cost (31-day month)**
- Lambda, direct-API design at 512 MB (A1, A2): ticks 4,464 x 3 s x 0.5 GB = 6,696 GB-s; runs 900 x 30 s x 0.5 = 13,500; posts 12 x 10 s x 0.5 = 60; total **20,256 GB-s**, 5,376 requests. Free tier: "one million requests and 400,000 GB-seconds per month" [S3] -> **$0**. Without it: 20,256 x $0.0000133334 (arm64) [S3][S3b] = $0.27 + 5,376 x $0.20/1e6 = $0.001 -> **$0.27**.
- Lambda, CLI design at 4 GB: ticks 4,464 x 3 x 4 = 53,568; runs 900 x 90 x 4 = 324,000; posts 480; total **378,048 GB-s** (inside 400,000 free, barely). Without free tier: x $0.0000133334 = **$5.04**. Plus the container image in ECR (price not researched). Splitting a 512 MB tick function from a 4 GB agent function lowers this.
- EventBridge Scheduler: 4,476 invocations; free up to 14,000,000/month, then $1.00/M [S5] -> **$0**.
- DynamoDB on-demand: writes ~4,464 (cursor per tick) + 900 x 8 (**Assumption**: ~8 writes per handled comment) + 36 = ~11,700 WRU x $0.625/M = **$0.007**; reads ~18,000 RRU x $0.125/M = **$0.002**; storage $0.25/GB-month, 25 GB free [S8].
- S3 alternative: 4,464 PUT x $0.005/1,000 = $0.022; 4,464 GET x $0.0004/1,000 = $0.002; storage $0.023/GB-month [S14] -> **~$0.03**.
- Secrets: Parameter Store standard parameters "No additional charge", standard-throughput API calls free [S7]; SecureString decryption uses KMS: AWS managed keys free to create/store, 20,000 requests/month free, then $0.03/10,000 [S15]. Worst case every invocation reads 3 parameters: 5,376 x 3 = 16,128 < 20,000 -> **$0**. Secrets Manager: $0.40/secret/month + $0.05/10,000 calls [S6]: 3 secrets (mail, publisher, LLM) = $1.20 + 16,128 calls = $0.08 -> **$1.28**; one bundled secret $0.40 + $0.03 = **$0.43**.
- CloudWatch Logs: 5 GB/month free (ingestion, storage, queries combined), then $0.50/GB [S16] -> **$0** (A4).
- **Total infrastructure: ~$0/month inside always-free limits with Parameter Store; ~$0.30-1.60/month without the free tier or with Secrets Manager.** LLM cost from section 1 on top.

**Free tier as of 2026 (verified).** Accounts created on or after 2025-07-15 get "up to $200 in credits": $100 at sign-up plus up to $100 earned [S1][S1b]. On the Free plan the account "closes on its own 6 months after you open it or when your credits run out, whichever comes first" [S1]; credits expire 12 months after account creation [S2]. Both plans keep "30+ AWS services ... always free within monthly usage limits" [S1]; the Lambda pricing page lists the Lambda allowance above [S3]. Accounts created before 2025-07-15 stay on the legacy program (12-month trials and always-free) [S1b]. Consequence: an always-on agent must be on the **Paid plan**, or it stops when the Free plan account closes at 6 months. Which services the Free plan excludes: not found (the FAQ says only "a subset") [S2].

**Limits and gotchas**
- 15-minute hard timeout [S4]; the runtime already stops at `timeout_seconds` and `max_events_per_tick` 5, but 5 CLI runs of 90 s plus the tick fits; 5 runs at 600 s does not. Cap per-tick work by time, not only by count.
- Cold starts: seconds for a small Python zip; larger for a 4 GB container with the CLI (**Assumption**, not measured).
- Filesystem: only `/tmp` is writable and is not kept between cold starts; SQLite must be rehydrated each tick (S3) or replaced (DynamoDB).
- Environment variables are limited to 4 KB in total [S4]: secrets go through SSM/Secrets Manager, not env config.
- New accounts "have reduced concurrency and memory quotas", raised automatically with usage [S4]: a 4 GB function may need a quota check on a new account.
- The launchd provider's approval model (hash of the command and files at approval) maps to the deployed code hash (**Assumption**: Lambda reports a `CodeSha256` per version; not re-verified today); a new scheduler provider (`eventbridge`) is needed.

**Ops burden:** low at run time (no OS to patch); medium-high to build: IaC or CLI scripts for function, schedules, IAM, parameters; a new store provider or S3 sync; a packaging step; a non-macOS notification channel (SNS e-mail, not priced here).

**Lock-in:** medium. The runtime's contract (CLI verbs for store, scheduler, secrets) keeps AWS in providers; the DynamoDB store and EventBridge scheduler are AWS-only code.

**Security:** secrets in SSM/Secrets Manager, readable only by the function's IAM role (least privilege per parameter path). No inbound network surface. Blast radius of the role: whatever the three secrets allow (read all Gmail, post and comment as the person, spend on the LLM key). Keep the AWS root account unused, MFA on, a budget alarm.

## 4. Serverless alternatives

### 4a. Cloudflare Workers + Cron Triggers + D1

- Status: Python Workers became GA on 2026-09-21 ("Python Workers are now generally available (GA)") [S23]; Python 3.14 available from compatibility date 2026-09-08 (changelog, seen in search results only). Packages: "pure and PyEmscripten Python packages on PyPI" plus those in Pyodide; "WebAssembly support for Python packages is still in early stages" [S24]. Runtime is Pyodide (CPython on WebAssembly) [S25].
- **Mapping:** cron trigger every 10 min (UTC only: "Cron Triggers execute on UTC time" [S26]) and cron triggers for the posts; state in D1 (a new store provider); secrets as Worker secrets (price not researched); LLM by `fetch` to the API. The Claude Code CLI cannot run here. `runtime.py` calls providers through `subprocess` and uses `fcntl`: **Assumption**: neither exists in Pyodide (the docs pages read do not mention subprocess or native binaries [S24][S25]). This option means **rewriting the runtime** as a single in-process Worker.
- **Limits** [S36]: Free plan 10 ms CPU per cron invocation, 50 subrequests, 5 cron triggers per account; Paid plan 30 s CPU for crons at < 1 h interval, 15 min wall time, 10,000 subrequests, 250 crons; 128 MB memory per isolate; CPU time excludes waiting on network. Whether a Python Worker's start-up fits in 10 ms of CPU: not verified; **Assumption**: plan on the Paid plan.
- **Cost** [S37][S38]: Free plan $0 (100,000 requests/day; D1 free 5 M rows read/day, 100,000 rows written/day, 5 GB). Paid: **$5/month** minimum, 10 M requests and 30 M CPU-ms included; D1 paid 25 B rows read and 50 M rows written/month included. Our volume (4,476 invocations) is far inside either -> **$0 or $5/month**.
- **Ops burden:** very low at run time; highest build effort (rewrite, new store, no CLI). **Lock-in:** high (Workers runtime + D1 bindings). **Security:** secrets in Cloudflare's secret store, no server to patch; blast radius = the Cloudflare account.

### 4b. Google Cloud Run jobs + Cloud Scheduler

- **Mapping:** a container with the current Python code as a Cloud Run job; Cloud Scheduler fires it every 10 min and at post times; secrets in Secret Manager, mounted as env vars; state in Firestore or a SQLite file synced to Cloud Storage with a generation precondition (**Assumption**: GCS has an equivalent of S3's `If-Match`; not verified today); SQLite on a mounted bucket is a network filesystem, same warning as EFS [S12].
- **Cost:** Cloud Run jobs free tier "First 240,000 vCPU-seconds ... First 450,000 GiB-seconds free per month"; after it $0.000018/vCPU-s and $0.000002/GiB-s (Tier 1); billed rounded up to 100 ms [S39]. Direct-API design (A1: 10 s per tick incl. container start; A2): 4,464 x 10 + 900 x 30 + 12 x 15 = **71,820 vCPU-s** (1 vCPU), 35,910 GiB-s (0.5 GiB) -> **$0** inside free tier; without it 71,820 x 0.000018 + 35,910 x 0.000002 = $1.29 + $0.07 = **$1.36**. CLI design (2 vCPU, 4 GiB for runs, **Assumption** on sizing): 206,640 vCPU-s and 346,320 GiB-s, inside the free tier; without it $3.72 + $0.69 = **$4.41**.
- Cloud Scheduler: $0.10 per job per 31 days; 3 jobs per billing account free; a paused job still counts [S40] -> 2-3 jobs = **$0**.
- Secret Manager: 6 active secret versions free, then ~$0.06/version-month; 10,000 accesses free, then $0.03/10,000 [S41]. 5 secrets, 4,476 x 3 = 13,428 accesses -> 3,428 billable -> **$0.01**.
- Artifact Registry: 0.5 GiB free, then $0.000136986/GiB-hour (~$0.10/GiB-month) [S42]. A slim Python image fits (**Assumption**); an image with the Claude Code binary may not.
- **Limits/gotchas:** container cold start on every tick (the tick is a job execution, not a warm service); job task timeout not verified today; cron in a chosen time zone (**Assumption**: Cloud Scheduler supports time zones; not verified today). **Ops:** low at run time, medium to build (Dockerfile, IAM, scheduler, state sync). **Lock-in:** medium (standard container; scheduler/secrets/state are GCP). **Security:** service account scoped to the secrets; no inbound surface.

### 4d. GitHub Actions scheduled workflows

- **Limits** [S45]: "The shortest interval you can run scheduled workflows is once every 5 minutes." "The `schedule` event can be delayed during periods of high loads ... High load times include the start of every hour." "If the load is sufficiently high enough, some queued jobs may be dropped." Scheduled workflows "only run on the default branch"; "In a public repository, scheduled workflows are automatically disabled when no repository activity has occurred in 60 days." Cron is UTC (**Assumption**, standard Actions behaviour; the page read does not restate it).
- **Cost:** public repositories free [S46]; private repositories on GitHub Free include 2,000 minutes/month [S46]; Linux 2-core x64 $0.006/min, arm64 $0.005/min; "GitHub rounds the minutes and partial minutes each job uses up to the nearest whole minute" [S47]. Ticks alone: 4,464 jobs x 1 min = 4,464 min; with comment runs taking a second minute (**Assumption**) up to ~5,376 min. Billable 2,464-3,376 min x $0.006 = **$14.78-20.26/month** (x64) or $12.32-16.88 (arm64). A 15-minute tick roughly halves it.
- **Mapping and fit:** state would have to be committed back to a repository or kept in an external store each run (no persistent disk); secrets as repository secrets (the resolver already supports this path, contracts/secrets.md). A public repository would expose run logs and state, which contain strangers' comments and the person's replies: not acceptable, and work data stays out of ai-workbench (a separate private repository would be needed). Dropped or delayed runs are documented. **Verdict:** the most expensive of the serverless options for a 10-minute tick and the least reliable; fine for the 12 posts/month on their own.

## 6. Cross-cutting findings

1. **The 4 GB rule decides the price class.** Keeping the Claude Code CLI on a server needs >= 4 GB RAM [S34]: cheapest found is Hetzner CX23 at €5.99/month (if available), then $20-29 elsewhere. A direct-API adapter (one Messages API or OpenRouter call, skill and brand files in the prompt, no tools) removes the rule and makes every option viable, from $0 serverless to a $4 droplet. It also keeps the "model has no tools that act" rule trivially true, and makes cost per reply predictable (section 1.3).
2. **Subscription on a server is the operator's decision.** Documented technically (`setup-token`), ambiguous in the Consumer Terms (section 1.1). An API key costs about $10-31/month at 300-900 Sonnet 5.5 replies, $1.3-3.9 on DeepSeek V3.2.
3. **Approvals need a way in.** `runtime.py approve` must run where the store is: SSH on a VPS; AWS credentials against DynamoDB/S3 from the Mac on Lambda. The publisher's ledger file must live next to the store in every serverless option.
4. **Notifications:** today's are macOS notifications; every option needs another channel (e-mail through the provider, or a chat bot). Not priced.
5. **The LinkedIn token expires every 60 days with no refresh** (providers/publisher/README.md): the person re-runs `auth.py` on a local machine (browser + localhost callback) and copies the token to the host's secret store. Every option needs that manual step; a `--check` warning under 7 days should reach the new notification channel.
6. **Gmail `gmail.readonly` reads the whole mailbox**, not only LinkedIn notifications: the largest privacy blast radius of the three secrets on any host. Prefer a host where only the tick's identity can read it (IAM role, service account) over a shared box.
7. **Timezones:** EventBridge Scheduler takes IANA zones [S5]; Cloudflare crons are UTC only [S26]; post times in a local zone need a fixed UTC offset there, which holds only in a zone without daylight saving time (not verified per zone).

## 7. Assumptions list

A1-A4 (section 0); ~8 store writes per handled comment; 30 s (API) and 90 s (CLI) per LLM run; 2 replies/hour for the 1-h cache case; a second billed minute for GitHub ticks with a comment; reserved concurrency 1 as the Lambda lock; DynamoDB conditional writes and Lambda `CodeSha256` from general knowledge; subprocess/fcntl unavailable in Pyodide; GCS generation preconditions, Cloud Scheduler time zones, Cloud Run job timeout not verified; Claude Code CLI caches automatically; the 15k-token prompt was not measured with Sonnet 5.5's tokenizer; Batch API turnaround unsuitable; IPv6 reachability of Gmail/LinkedIn/LLM APIs unverified; daylight saving time in the posting zone.
