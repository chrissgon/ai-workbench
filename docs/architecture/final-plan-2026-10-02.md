# Final plan, 2026-10-02: everything that remains, ordered around one last measurement round

**This is the plan in force.** It replaces `docs/architecture/plan-2026-10.md`, whose phases 0 to 4 are done and whose phases 5 and 6 are absorbed here. It is built from the audit of 2026-10-02 (`docs/architecture/audit-2026-10-02/`, nine reports), amended after two critical reviews of the plan itself (section "Review of 2026-10-02 and what it changed"), and from the triage of every item of `docs/backlog.md`. Its section "Decisions for the maintainer" awaits the maintainer; nothing in it is decided until they say so, except what the section marks as already approved.

## Purpose and the one rule that orders everything

- The 48 skills were measured once in the eval container. They are measured **one more time, and that round is meant to be the last** for the skills as they are.
- **The rule:** anything that changes a skill's folder, or that changes what a run measures (the eval runner, the adapters, the container image, the grading template, the gate), is finished **before** that round. After the round those things are frozen; changing one of them means measuring again.
- So the order is: repairs that touch neither (phase A), the measurement itself, changed once (phase B), every skill edited once (phase C), a dry run (phase D), the round (phase E), and only then the work that is independent of skills (phases F to H).
- Everything that is known to need fixing is fixed before the round, even though it costs the measurement of all 48 skills: the audit exists so that no known defect is left to cause a second round.
- This document covers everything that remains to be done in the repository. The "Backlog map" near the end lists every backlog item and where this plan handles it, so that nothing is lost.

### Terms used below

| Term | Meaning |
|------|---------|
| Skill folder | `skills/<name>/`: `SKILL.md`, `references/`, `assets/`, `scripts/`, `evals/`. Its content hash leaves out `scripts/tests/`, `evals/platforms/` (decision 14c) and the record itself. |
| Case, assertion | A case is one prompt with its fixture files in `skills/<name>/evals/evals.json`; an assertion is one statement about the output that a grader judges true or false. |
| Variant | One of four ways a case is run: with the skill or without it, on the strong model or on the floor model. |
| Strong model, floor model, grader | The two models under test and the model that judges assertions, all named in `evals/eval-gate.json`. |
| Run, iteration | A run is one execution of one case in one variant. An iteration is every run of a skill (every case, four variants, the configured number of runs each). |
| Record | `skills/<name>/evals/result.json`: the result of a complete iteration, with the hash of the skill folder. Its optional `platforms` section is the one named exception: each entry is written by a run of one platform's cases (decision 14c). |
| `evaluated`, `stale`, `draft` | The status computed from the record: the gate passed on the current content; it passed but the folder or the measurement changed since; there is no passing record. |
| Gate | The rule a skill must pass: both models at 0.8 or more with the skill, and the strong model with the skill not more than 0.05 below the strong model without it. |
| Measurement version | A number in `evals/eval-gate.json`, raised by hand when a change alters what a run measures. It is 4 today; phase B ends by raising it to 5. |
| Round | The measurement of all 48 skills under one measurement version. The first round closed on 2026-10-02 (backlog T11). |
| Freeze | The state after the final round: the files that define the measurement and the skill folders do not change without a new measurement. |
| Report references | `(harness §3)` is section 3 of `audit-2026-10-02/harness.md`; `(cross-skill §1c)` a section of `cross-skill.md`; `(group-3, design-brief, must-fix 2)` an item of a group report; `(backlog N1)` an item of `backlog.md` in the audit folder. Decision letters and numbers of the reports are written `harness A`, `cross-skill 7`, `backlog Q3`. |
| Size | S: under an hour. M: a few hours. L: a day or more. The sizes are the audits' own. |

## Review of 2026-10-02 and what it changed

The plan was reviewed twice on 2026-10-02, read-only: once for its internal consistency and once against the code and the architecture. The two reports are kept as written in `audit-2026-10-02/plan-review-consistency.md` (2 blockers, 19 should-fix, 9 nits) and `audit-2026-10-02/plan-review-architecture.md` (5 blockers, 10 should-fix, 6 nits). This version resolves all 7 blockers, all 29 should-fix findings and 14 of the 15 nits; the remaining nit (a status line saying which decisions are answered) is the maintainer's to write, and only its part about decision 2 is applied.

Most findings took the smallest edit their report proposed. Seven did not: the resolutions below are the lead's, and each is **proposed after the review of the plan, awaiting the maintainer's confirmation**. Where the plan applies one, it says "(R1)" to "(R7)".

- **R1. Decision 14a, narrowed.** Only the four class names change. The provider folders do not move and the `<CLASS>_PROVIDER` variables keep their names: `providers/resolve.py` maps a class name to its existing folder, and keeps reading the four old names as aliases. Moving folders would have dropped provider tests from CI, emptied the Python 3.9 guard, broken the hook's path mapping, the providers' secret lookup and jobs already scheduled on users' machines, for no gain a skill can see. No migration is needed in a project. C0.2 becomes M with its real file list.
- **R2. Decision 14c, cases and hash.** A platform's cases live in `skills/<name>/evals/platforms/<platform>.json`, outside the skill's content hash. The base gate is computed on `evals/evals.json` only. The record gains a `platforms` section written by `eval_run.py --platform <name>`; the status shows `measured`, `not measured` or `stale` per platform, as a report and never as a warning. The fingerprint leaves out `shared/references/platforms/`. The pilot exercises the path once.
- **R3. Decision 14c, what "never edits a skill" covers.** Knowledge goes in `shared/references/platforms/<platform>.md`, simple machine data in `<platform>.json` beside it, read by a script through a path given by flag. A parser that is code for one platform stays in its skill behind `--platform`; a platform that needs a new parser edits that one skill, which is measured again. Rule 3 of decision 14b says so.
- **R4. `shared/` outside evals.** Installations get `shared/references/` once, in C0.9, in the files that really build them; default 31 and lane F3 no longer plan it. The API adapter sends the platform reference the task names. In evals, `shared/references/` is staged only into with-skill runs; script sources and tests are never staged.
- **R5. Strict and the round's exit.** The exits ask for zero errors and for no warning other than the ones the plan lists by name. A `draft` skill after the round is a listed outcome, accepted by `--strict`, not a failure of the exit.
- **R6. The fingerprint.** It covers every file that decides what a run measures, the executor, the staging code and each eval adapter's `adapter.json` included. `runs`, `timeout_seconds` and `retries` have one home (the gate file) and the refusal markers one (the adapter's data). What a later phase would change inside it is moved before the freeze or named in "What would make a second round necessary".
- **R7. Decision 11 leftovers.** Every row that still said invented numbers or fiction is rewritten to the narrowed rule. `AGENTS.md` is reworded in the three places that say numbers go, in one item of phase A (A10), together with the product-name rule and the four design rules.

Findings left as they were, because they did not hold on re-reading: the consistency report's count of rows shaped by decision 11 (14 against 18) is moot now that the decision is taken and the rows are rewritten; its claim that `evals/README.md` (C0.7) is inside the fingerprint is not so; most of the architecture report's table of what a folder move breaks no longer applies, since the folders do not move (R1).

### The main patterns the audit found

Across the 48 skills (the group reports' "Patterns" sections):

1. **Reports state that a check was done instead of quoting it.** The grader sees only the reply and the files a run leaves. "The lint is run and reports ok" fails good runs or passes on a sentence. It is the main cause of failures with the skill in the design, product and engineering groups.
2. **Assertions about what did not change** ("X is unchanged", "no file is modified", "the file is deleted") fail good runs, because an unchanged or deleted file is invisible to the grader.
3. **Script paths that exist only in the workbench.** 31 of the 37 skills with scripts write `scripts/<name>` or `skills/<name>/scripts/<name>`; a model first looks in the project, and artifacts end up carrying the path of an AI tool's folder.
4. **Stop gates without the words that make them hold**: nothing says that "go" is not an answer or that nothing is written before the answer; several gates sit inside a long step or only in the Inputs table; several have no template for the reply that asks.
5. **Cases that measure nothing**: about 30% of the assertions pass in every variant; several cases score the same with and without the skill; conditional assertions ("If X exists, ...") pass when nothing is written.
6. **Undeclared reads and writes**: 25 skills write the state file without declaring it; seven paths have several producers; nine skills use a requirement class or produce a side effect they do not declare.
7. **Two things that must be last**: the reply "ends with" the external-content section and also "ends with" a question; it costs `flow-fix-bug` seven assertions.
8. **Fixtures**: runtimes the image does not have (Node 20 and 22 in eleven copies of one project), a lint that cannot run, real hosts and one real person's name, dates relative to the day of the run, placeholders where a small real project is needed, and several fixtures and "Gotchas" that still carry one real case's numbers, dates and decisions (principle 8).
9. **Nine scripts end in a traceback** when a flag comes last without its value; most hand-written parsers ignore an unknown flag silently.

In the harness (harness report, summary table):

1. **The grader is inconsistent, not biased**: 4.4% of re-judged verdicts were wrong and 11.9% doubtful, most from what the template does not say and from what the grader cannot see. The same sentence passed in one iteration and failed in the next; one skill of nine crossed the gate on a rerun with nothing changed.
2. **Three runs per case are few**: one iteration's mean moves by about 0.045 between identical reruns.
3. **The early-end detector** was wrong in 7 of its 12 detections, all on the strong tier.
4. **A run can read more than it should** (the whole `adapters/` folder, a second copy of the skill), and the floor provider's key is printed in 14 stored transcripts outside the repository.
5. **The image is not reproducible** (tags, a moving package index, one machine's local build), its scratch folder for the floor runner is not writable (67 runs), and the host's time zone leaks into it.
6. **The contamination check cannot fire** in the container; a timeout is silently dropped; nothing stops a change to the template or the image without raising the version.

### (a) Decisions that change the plan

**1. How many runs per case in the final round?** (harness §2, harness A)

| Option | Consequence |
|--------|-------------|
| 3, as today | 12 runs per case; about 21 hours of compute for today's 141 cases. A skill at 0.84 fails about one round in five by chance. |
| 5 for every skill | 20 runs per case; about 35 hours for 141 cases, about 130 USD more in notional strong-model and grading cost. One standard, no rule to explain. |
| 3, plus 2 more for a skill within two standard errors of a limit | About 24 hours; cheaper, but a record then depends on a rule applied after seeing scores. |

Recommendation: **5 for every skill**, written in `evals/eval-gate.json` so that a record with fewer cannot be written. Needed before phase B.

**2. Is every run graded once or twice?** (harness §1 "A grader other than the model under test", harness B; backlog Q4c and N4)

| Option | Consequence |
|--------|-------------|
| Once, by the configured grader, with the new template, the facts block and no tools | No extra cost. Removes the causes of the 11 wrong verdicts found; the remaining random inconsistency stays unmeasured. |
| Twice, with a third grading when the two differ on an assertion | At least twice the grading calls (about 5 more hours of compute and 120 to 150 USD notional at 5 runs). Disagreement becomes a number in the record. |
| A different model as grader | A third provider, adapter path and key the day before a final round; the sample shows inconsistency, not self-preference. |

Recommendation: **twice in the final round**, because the grader is the larger source of noise between identical iterations and this round is meant to stand. It is built as a number in the gate file (`grading_passes`); the pilot of phase D reports the disagreement rate, and the maintainer may drop to one pass if it is under 1% of assertions; that is decided at D4, before phase D's exit fixes the fingerprint. `integration:*`, `search:web`, `generator:*` and `publisher:<platform>` keep their names.

**Narrowed after the review of the plan (R1; proposed after the review of the plan, awaiting the maintainer's confirmation).** Only the class names change. They change in `contracts/environment.md`, in skills' `requires`, in the orchestrator's class table, in `providers/CONTRACT.md`, in the class list of `providers/resolve.py` and in the class names the runtime passes to it. Nothing else moves:

- **The provider folders stay where they are**, and so do the `<CLASS>_PROVIDER` environment variables. `resolve.py` maps a class name to its existing folder: `reader:email` to `providers/mailbox/` (`MAILBOX_PROVIDER`), `scheduler:job` to `providers/scheduler/` (`SCHEDULER_PROVIDER`), `store:runtime` to `providers/store/` (`STORE_PROVIDER`), `sender:email` to `providers/mailer/` (`MAILER_PROVIDER`; no implementation ships today), as `integration:vcs` already maps to `providers/vcs/`. `providers/secrets/` is not a class and is untouched.
- **Why the folders do not move.** A move to `providers/<role>/<target>/` would silently drop the provider tests from CI (`scripts/test_dirs.py` finds `providers/*/tests`), empty the globs of the Python 3.9 guard, break the pre-commit hook's path mapping, break every provider's lookup of the secrets resolver (a path relative to its own file) and break the jobs already scheduled on users' machines, which run copies that name the old paths. A skill sees a class name and the path the resolver prints, never a folder: the move buys it nothing.
- **No migration in a project.** The variables keep their names; the keys of a project's `runtime.json` (`mailbox`, `store`, `scheduler`, `publisher`) are configuration keys and do not change (the runtime maps them to the new class names); the data names (the scheduler's folder and job label, the ledgers, the keyring user names, `STORE_SQLITE_PATH`, `SCHEDULER_HOME`) never change. `resolve.py` keeps reading the four old names as aliases of the new ones, so a recurring job scheduled before the rename, whose copy of the runtime still asks for `store`, keeps running. The validator is where a bare name is refused: in a skill's `requires`.
- **Two forms of a class.** `<role>:<target>` with a fixed target, where the target is part of the class's identity and another target has other verbs: `reader:email`, `sender:email`, `scheduler:job`, `store:runtime`, `search:web`, `integration:vcs`, `integration:issue-tracker`, `integration:design-tool`, `generator:image`, `generator:video`. And `<role>:<parameter>`, where the part after the colon is handed to the provider: `publisher:<platform>` only, whose platform is passed as `--platform` to one implementation that may serve several. As the code stands, `generator` is the first form: the resolver gives its two kinds one folder and a shared fallback variable, as it does for `publisher`, but the contract lists them as two fixed classes and no verb receives the kind as an argument.
- **How many skills this touches.** A grep of `requires:` in `skills/*/SKILL.md` finds two bare classes: `mailbox` in `mkt-engage` and `scheduler` in `mkt-publish`; `mailer` and `store` are declared by no skill. After default 57 takes `mailbox` out of `mkt-engage`, one skill declares a bare class. The rename is still done now, because the class table of the orchestrator and the body of both skills name the classes and a rename after the round would stale all three.

Done in C0.2 for everything outside the skill folders; the three skill folders that name a renamed class (`mkt-publish`, `mkt-engage`, `core-orchestrator`'s class table) change in their own rows, so that each skill is still edited once. The validator's rule that rejects a class without a role is a warning until the last group batch merges and an error after it, as the contract rules of C0.1 are.

**14b. Four design rules, written into `AGENTS.md`** (decided by the maintainer on 2026-10-02, after weighing low coupling against what a floor model can follow). They are the part of the SOLID principles that holds for text a model interprets:

1. A skill names no harness (principle 1, already enforced).
2. A skill's procedure names no social platform. It declares the class it needs and reads what is specific to a platform from that platform's reference (decision 14c). What a user types in a request may name a platform.
3. Adding a platform adds a reference file, a data file where a script needs one, and, where something is executed, a provider. It never edits a skill's procedure, and only that platform is measured. Two exceptions, said plainly (R3; proposed after the review of the plan, awaiting the maintainer's confirmation): a skill whose script parses a platform's own format carries that parser as code (the comment-link parser of `mkt-engage`, the profile-export parser of `brand-profile`), and adding a platform that needs a new parser edits that script, so that one skill is measured again in full; and `brand-name`'s table of networks to check is inside that skill, so a row added there stales that skill.
4. One skill per job. A skill is split only when the part has its own trigger (someone would ask for it alone), its own requirements or side effects, or its own artifact. Smaller is not a goal: every installed skill costs a line of the listing budget, a flow to compose it and a full evaluation. No skill is split before the round.

Not adopted, with the reason: a formal profile contract with declared capabilities, and a validator rule that refuses platform names, wait until a second platform is built, because a contract drawn from one example describes that example. The code host is out of scope: no second host is planned, decision 5 installs its command-line tool in the image so that the branch that uses it is measured, and `ops-repo-baseline` has the host as its subject.

**14c. Platform references, measured per platform** (decided by the maintainer on 2026-10-02; inventory in `audit-2026-10-02/platform-inventory.md`).

- Where: `shared/references/platforms/<platform>.md`, one file per social platform, read by a skill at `../../shared/references/platforms/<platform>.md`. It holds what the platform is as a medium: text limits, media it requires, how links behave, the shape of a post's URL, what can be read from outside. What belongs to one implementation (credentials, that service's errors, how to call it) stays in the provider: one provider may serve several platforms, and three of the skills that need platform knowledge declare no publisher.
- The step in a skill is literal: "read the reference of the platform the request names; if there is no such file, stop and say the platform is not supported". A skill reads only that one file.
- Scripts take `--platform`. Simple machine data a script needs (URL patterns, host names, length limits) is in `shared/references/platforms/<platform>.json`, beside the reference, and the script reads it through a path given by flag (`--platform-file <path>`; the skill's step passes it), never from a table in the skill and never by a relative path of its own, because a scheduled job runs scripts from a flat folder of copies. So adding a platform does not edit the script. A parser that is code for one platform stays in its skill behind `--platform` (rule 3 of decision 14b). The callers outside the skills follow in the same pull request as the script they call: `scripts/runtime.py` runs `parse_notification.py`; `scripts/runtime_vote.py` and `scripts/vote_job.py` run `vote_update.py`; `scripts/runtime_vote.py` runs `payload.py`, and the snapshot it hands the scheduler carries the platform's data file under its own name (R3; proposed after the review of the plan, awaiting the maintainer's confirmation).
- Scope now: the first reference (the one platform built today) and the seven skills that carry its knowledge (`brand-identity`, `brand-name`, `brand-profile`, `brand-strategy`, `mkt-engage`, `mkt-publish`, `mkt-vote-round`). `brand-name`'s list of networks to check stays a table inside that skill. References for other platforms are written when each has a real task, never from general knowledge.
- Measurement (R2; proposed after the review of the plan, awaiting the maintainer's confirmation):
  - The cases of a platform live in `skills/<name>/evals/platforms/<platform>.json`, with their fixtures under `skills/<name>/evals/platforms/<platform>/files/`. That folder is outside the skill's content hash, for the reason `scripts/tests/` is: the adapters remove `evals/` from the copy a model sees, so it changes nothing the base cases measure. Adding a platform's cases therefore makes no skill stale.
  - The base gate is computed on `evals/evals.json` only and is untouched by platforms: a platform whose cases fail never turns an `evaluated` skill into `draft`. The cases the seven skills have today stay in `evals/evals.json` and are the base.
  - The record gains a `platforms` section, written by `eval_run.py --platform <name>` and refused unless the base record is of the current content hash, measurement version and models. Each entry holds the hash of the reference (and of its data file), the hash of the case file, the four scores, and its own pass: both models at the threshold with the skill.
  - The status shows, per platform, `measured`, `not measured` or `stale` (its reference, its data file or its case file changed). These are reported in the status table; they are never warnings, so they never fail `--strict`.
  - A platform reference is outside the measurement fingerprint (default 21 yields here): its hash is in the record. The base record also names the hash of each platform reference staged into its with-skill runs; when the first platform's reference is edited, the skills whose base cases read it read `stale`, and nothing else does.
  - The pilot of phase D exercises the `--platform` path once.
- Installations get `shared/references/` beside the skills in C0.9, before the round (R4); until B2 only the eval adapters copy it.

#### The rule for case changes

- An assertion changes only for a stated reason: it never influences the score (it passes in every run of every variant and is a language assertion or content any model produces); it fails a good output for a formality; it rests on something the grader cannot see; it is conditional; or it contradicts the skill. When the output is not good, the skill is fixed, never the assertion.
- A guard (something that must not happen) is kept even when it always passes, and is reworded so that the grader can verify it.
- A content assertion that always passes is replaced by a sharper one that the audit's evidence shows the baseline failing; a replacement that still passes everywhere in the final round is listed in the round's report and left alone until the skill is next changed.
- **Every assertion change is listed before and after in the pull request**, with its reason; so is every change to a prompt, an expected output or a fixture.
- A new case follows C0.7 and is listed with the behaviour it measures.
- Once phase C is merged, the cases are frozen for the round. During the round a case changes only through the repair loop of phase E, under the same rule.

**A skill that fails.** The round must end, so the loop has a limit:

1. An incomplete iteration (infrastructure) is resumed with `--resume`, never scored, and does not count as an attempt.
2. A complete iteration that fails the gate is read: the failed gradings, the replies, and for the floor tier the transcript. Each failure is classified as a skill defect, a case defect, or the instrument.
3. The instrument (the harness, the template, the image) is never changed inside the loop. If the reading shows a defect there, the round stops, the cause is fixed, the version and fingerprint are raised, and every record already made under version 5 is measured again. This is what phases B and D exist to prevent.
4. A skill defect is fixed in the skill; a case defect is fixed in the case under the rule for case changes, listed before and after. The skill is then measured again in full, alone. That is one repair.
5. A skill whose failing score is within two standard errors of the threshold, and whose failed gradings show neither kind of defect, is measured once more unchanged; the record carries the number of attempts. A second failure is treated as a defect to find.
6. **At most two repairs per skill**, three complete measurements in all. A skill that still fails keeps its failing record, reads `draft`, gets a backlog item that names what was tried, is entered by name with that item in the gate file's `known_draft` list, and leaves the round. This is a listed outcome of the round, not a failure of its exit (R5; proposed after the review of the plan, awaiting the maintainer's confirmation). The round then closes with fewer than 48 `evaluated`, stated in the decisions log; it is not held open.
7. A passing record is never measured again to improve it. `marginal` is information, not a reason to rerun.

## What would make a second round necessary

After the round, each of these stales all 48 skills, or enough of them to amount to a round. They are the things that must not change, or must change only on purpose:

- the grading template, or what the runner gives the grader (the facts block, the input files, the number of passes);
- the image: its definition, a tool added or removed, the versions of the two runners, its platform;
- either eval adapter's `run-prompt.sh` or `adapter.json`, including flags that change what a model may do or see; the executor; the staging module (`scripts/stage_skills.py`), which the installers of lane F3 import and must not change;
- the measurement constants (runs, timeout, retries, early-end phrases, refusal markers, the file limit) and the gate's rule, threshold or tolerance;
- the strong model, the floor model or the grader;
- `shared/references/` other than `platforms/`, which every with-skill run receives;
- a change of convention applied to every skill afterwards: a new required frontmatter key, shorter descriptions for the listing budget (decision 9, third option), a new canonical sentence, a renamed requirement class, a validator rule that existing skills fail;
- a change to the source of a script that many skills carry as a generated copy, or to a fixture family shared by many skills;
- the credential sidecar or the local-model tier built into the executor (lane F7).

These cost one skill's measurement, not a round, and are normal work after the freeze: a fix or a new version of one skill; a new case for one skill; a planned skill that gets built (plus the orchestrator, once per batch); a description changed after the routing measurement; a change to any skill's `outputs` or `updates`, which also regenerates the owner table and so stales `core-orchestrator`; a new parser for a platform, or a row in `brand-name`'s table of networks (that one skill); any edit of a file a case brings through `workbench_files` (`AGENTS.md`, the security scan, the harness files), which stales `core-skill-creator` alone.

These cost one platform's cases, not a skill's measurement: a platform reference, its data file or its case file added (`eval_run.py --platform`, in each skill that has cases for it). An edit to the reference of a platform already measured costs more: the base of each skill whose base cases read it, and that platform's cases.

These cost nothing: tests of skill scripts; everything under `providers/`, `scripts/`, `contracts/`, `templates/`, `docs/`, the installers and the runtime, as long as no skill folder, no frozen file and no file a case brings through `workbench_files` changes.
