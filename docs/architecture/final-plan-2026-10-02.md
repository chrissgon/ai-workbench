# Final plan, 2026-10-02: everything that remains, ordered around the first full test of the 48 skills

**This is the plan in force.** It replaces `docs/architecture/plan-2026-10.md`, whose phases 0 to 4 are done and whose phases 5 and 6 are absorbed here. It is built from the audit of 2026-10-02 (`docs/architecture/audit-2026-10-02/`, nine reports), from the triage of every item of `docs/backlog.md`, from two rounds of review of the plan itself, from an independent review of the repository and of the plan, and from the reliability model, its own independent review and that reviewer's reading of the pull request that carried the model (section "Reviews"). Every decision in it was taken by the maintainer on 2026-10-02. How skills are tested and ranked is the reliability model, stated in [`reliability-model-2026-10-02.md`](reliability-model-2026-10-02.md): that document describes the model, this one describes the work, and this plan already contains every consequence of the model.

## Purpose and the one rule that orders everything

- The 48 skills were measured once in the eval container, under a rule of three computed states in which any change to a skill discarded its record. That rule is replaced by the reliability model: a skill is ranked by the lab tests it has passed, a new skill gets a full test once, and later changes are carried by small tests.
- **Phase E is the first full test of the 48 skills under the model. It is the last of nothing.** No freeze follows it: a later change to a skill or to the measurement costs what the model's table "What a change costs" says, which for most changes is a few runs of one skill (section "What a change costs now" here says which item builds each row).
- **The rule that still orders the work:** anything known to need fixing in a skill folder, in a case or in what a run measures (the eval runner, the adapters, the container image, the grading template, the gate) is fixed **before** phase E. Phase E runs every case of every skill, with and without the skill, and that is cheapest done once, on content that is already right; and the changes of phase B alter what the grader sees, which is the one kind of change that discards lab evidence.
- So the order is: repairs that touch neither (phase A), the measurement and the evidence tooling (phase B), every skill edited once (phase C), a dry run (phase D), the full test (phase E), and then the work that is independent of skills (phases F to H). Phase P, the hardening of the providers and the runtime, is a lane of its own beside all of them: it touches no skill folder and no file the measurement fingerprint covers, and it does not gate phase E.
- This document covers everything that remains to be done in the repository. The "Backlog map" near the end lists every backlog item and where this plan handles it, so that nothing is lost.

## Open for the maintainer

Nothing is open. The points that were put to the maintainer, all answered on 2026-10-02:

- **The full test is deferred; the adjustments come first.** Decided when the work started: the skills were measured many times in the first round, the full test is the slowest part, and under the model nothing forces it. So phases A, B, C, C0 and P are carried out now; phase D keeps only what is cheap (its static checks, the smoke pass of every case once, and the guard cases of the skills that declare a side effect, run before those skills are used for real again); the pilot of D3, the reading of D4 and the whole of phase E wait for a battery of full tests that the maintainer starts later. Until then the 48 skills read `needs a test`, which is the honest label, and a skill gets its full test earlier only when the smoke pass shows a problem.

- **How skills are tested.** The reliability model, in the simpler version its independent review recommends, with every correction that review proposes.
- **Field evidence never promotes a skill by itself.** After a change of behaviour a skill returns to `reliable` only with lab runs: 3 to 9, the affected cases and the guard cases.
- **`reliable` requires a pessimistic score of 0.70 or more.** A small skill that has just passed its full test with a marginal mean therefore starts in `watch`. "Done" for a new skill remains "its first full test passed".
- **a. Web cases of the strong tier run with a low-limit API key instead of the account's token (FR-I10).** A web case runs with the network open and every tool allowed; with a key, a leak costs at most the key's limit. The cost is real money, for about 9 cases in 5 skills; the maintainer creates and stores the key (default 17, B5, the maintainer's actions of phase A).
- **b. What happens if the pilot shows that phase E does not fit the account (FR-I13).** The first step of the fallback that was agreed, a second grading pass only near the threshold, has no object any more: every run is graded once (decision 2). What remains of it: grading goes through an API key. Agreed before D4, so that it is not decided after seeing scores.
- **c. A recorded approval and a later push (FR-I8).** `ops-branch-sync` is aligned with `ops-pull-request` and with `contracts/environment.md`: a later push is covered only by a `standing` approval with bounds and validity, and the fixtures of both skills' new cases use such a row (rows 39 and 41).

### The main patterns the audit found

Across the 48 skills (the group reports' "Patterns" sections):

1. **Reports state that a check was done instead of quoting it.** The grader sees only the reply and the files a run leaves. "The lint is run and reports ok" fails good runs or passes on a sentence. It is the main cause of failures with the skill in the design, product and engineering groups.
2. **Assertions about what did not change** ("X is unchanged", "no file is modified", "the file is deleted") fail good runs, because an unchanged or deleted file is invisible to the grader.
3. **Script paths that exist only in the workbench.** About 31 of the 37 skills with scripts (30 to 32, by the criterion used) write `scripts/<name>` or `skills/<name>/scripts/<name>`; a model first looks in the project, and artifacts end up carrying the path of an AI tool's folder.
4. **Stop gates without the words that make them hold**: nothing says that "go" is not an answer or that nothing is written before the answer; several gates sit inside a long step or only in the Inputs table; several have no template for the reply that asks.
5. **Cases that measure nothing**: about 30% of the assertions pass in every variant; several cases score the same with and without the skill; conditional assertions ("If X exists, ...") pass when nothing is written.
6. **Undeclared reads and writes**: 25 skills write the state file without declaring it; seven paths have several producers; nine skills use a requirement class or produce a side effect they do not declare.
7. **Two things that must be last**: the reply "ends with" the external-content section and also "ends with" a question; it costs `flow-fix-bug` seven assertions.
8. **Fixtures**: runtimes the image does not have (Node 20 and 22 in nine of the eleven copies of one project), a lint that cannot run, real hosts and one real person's name, dates relative to the day of the run, placeholders where a small real project is needed, and several fixtures and "Gotchas" that still carry one real case's numbers, dates and decisions (principle 8).
9. **Nine scripts end in a traceback** when a flag comes last without its value; most hand-written parsers ignore an unknown flag silently.

In the harness (harness report, summary table):

1. **The grader is inconsistent, not biased**: 4.4% of re-judged verdicts were wrong and 11.9% doubtful, most from what the template does not say and from what the grader cannot see. The same sentence passed in one measurement and failed in the next; one skill of nine crossed the gate on a rerun with nothing changed.
2. **Three runs per case are few**: the mean of one complete measurement of a skill moves by about 0.045 between identical reruns.
3. **The early-end detector** was wrong in 7 of its 12 detections, all on the strong tier.
4. **A run can read more than it should** (the whole `adapters/` folder, a second copy of the skill), and the floor provider's key is printed in 14 stored transcripts outside the repository.
5. **The image is not reproducible** (tags, a moving package index, one machine's local build), its scratch folder for the floor runner is not writable (67 runs), and the host's time zone leaks into it.
6. **The contamination check cannot fire** in the container; a timeout is silently dropped; nothing stops a change to the template or the image without raising the version.

### (a) Decisions that change the plan

**1. How many runs per case?** (harness §2, harness A) **Replaced by the reliability model.**

Decided now: **3 runs per case**, written as `runs` in `evals/eval-gate.json`; lab evidence is written only by an event that uses the configured number (B5).

What it replaces: 5 runs for every skill, a pooled second measurement for a skill that failed inside the margin `max(2 x SE, 0.07)`, and a reported state for a score inside that margin. All three protected a single verdict from the draw, because that verdict was then frozen. Under the model nothing is frozen: evidence accumulates; a second full test of an unchanged version adds its runs to the first and replaces none; a partial test never moves the gate (MB3); and a skill that passes with a marginal mean starts in `watch`, because `reliable` needs a pessimistic score of 0.70 (MI2). The reviewer's measurement of what one draw of 3 runs can do stands as a known limit: with the movement of 0.045 between identical measurements, a skill whose true mean is 0.78 passes 33% of the time and one at 0.84 fails 19% of the time (MI8). The threshold of 0.70 is what keeps that from becoming a label.

**2. Is every run graded once or twice?** (harness §1 "A grader other than the model under test", harness B; backlog Q4c and N4) **Replaced by the reliability model.**

Decided now: **once**, by the configured grader, with the new template, the facts block and no tools (B3). There is no key for a number of grading passes. One exception: a guard verdict that fails with the skill is graded a second time before it counts against the guard rule, and that second grading changes no score (the model's section 4; B14).

What it replaces: two passes with a third on disagreement, chosen because the grader was the larger source of noise between identical measurements and the verdict was meant to stand. Under the model the grader's noise is averaged over accumulating runs and matters only near a threshold. It is still measured: D4 grades the pilot's stored replies a second time with an option of the runner that writes no evidence, and reports the disagreement rate. The same option compares a new grader with the old one (the model's section 9). No change of grader model: the grader is its own key of the gate file and stays fixed while its provider serves it, also when the reference model changes (MI4).

**3. How is the measurement protected from an unnoticed change?** (harness §7 "The freeze", harness H; backlog action plan step 4) **Replaced by the reliability model.**

Decided now: **a fingerprint of the files that decide what a run measures, and no freeze.** `evals/eval-gate.json` carries the fingerprint; `validate.py` fails when the recomputed one differs; the runner refuses to write evidence when it differs and writes the value into every evidence line (B10, MI12). A change to one of those files is committed as one of three kinds, each with its own consequence (the model's section 8): grader side, which raises the measurement floor and discards lab evidence; execution side, which is an epoch for the skills it affects; infrastructure, which costs nothing. The files the fingerprint covers are listed once, in B10 (PR6).

What it replaces: the fingerprint together with a strict mode of the validator in CI, switched on after the measurement of the 48, under which a pull request that changed a skill folder was red until that skill's new record was in it, and a list of skills accepted as not passing. CI now fails only on what the model's section 5 lists, the one place where that list is kept. It never fails on a score or on a band.

**14a. Requirement classes all take the form `<role>:<target>`.** It reverses the entry "requirement classes are not renamed" of backlog T20. Four classes are bare today while the others carry a prefix; renaming one later is a Y change of every skill that names it, so it is done now, while all 48 are being edited.

| Today | Becomes |
|-------|---------|
| `mailer` | `sender:email` |
| `mailbox` | `reader:email` |
| `scheduler` | `scheduler:job` |
| `store` | `store:runtime` |

`integration:*`, `search:web`, `generator:*` and `publisher:<platform>` keep their names.

Only the class names change (PR1). They change in `contracts/environment.md`, in skills' `requires`, in the orchestrator's class table, in `providers/CONTRACT.md`, in the class list of `providers/resolve.py` and in the class names the runtime passes to it. Nothing else moves:

- **The provider folders stay where they are**, and so do the `<CLASS>_PROVIDER` environment variables. `resolve.py` holds no map today: its `folder()` and `variables()` derive both from the text of the class, which is how `integration:vcs` reaches `providers/vcs/`, and by that derivation `reader:email` would give `providers/reader/` and `READER_EMAIL_PROVIDER`. An explicit table for the four renamed classes is therefore new work in C0.2, and `providers/CONTRACT.md` changes with it (FR-M5): `reader:email` to `providers/mailbox/` (`MAILBOX_PROVIDER`), `scheduler:job` to `providers/scheduler/` (`SCHEDULER_PROVIDER`), `store:runtime` to `providers/store/` (`STORE_PROVIDER`), `sender:email` to `providers/mailer/` (`MAILER_PROVIDER`; no implementation ships today). `providers/secrets/` is not a class and is untouched.
- **Why the folders do not move.** A move to `providers/<role>/<target>/` would silently drop the provider tests from CI (`scripts/test_dirs.py` finds `providers/*/tests`), empty the globs of the Python 3.9 guard, break the pre-commit hook's path mapping, break every provider's lookup of the secrets resolver (a path relative to its own file) and break the jobs already scheduled on users' machines, which run copies that name the old paths. A skill sees a class name and the path the resolver prints, never a folder: the move buys it nothing.
- **No migration in a project.** The variables keep their names; the keys of a project's `runtime.json` (`mailbox`, `store`, `scheduler`, `publisher`) are configuration keys and do not change (the runtime maps them to the new class names); the data names (the scheduler's folder and job label, the ledgers, the keyring user names, `STORE_SQLITE_PATH`, `SCHEDULER_HOME`) never change. `resolve.py` keeps reading the four old names as aliases of the new ones, so a recurring job scheduled before the rename, whose copy of the runtime still asks for `store`, keeps running. The validator is where a bare name is refused: in a skill's `requires`.
- **Two forms of a class.** `<role>:<target>` with a fixed target, where the target is part of the class's identity and another target has other verbs: `reader:email`, `sender:email`, `scheduler:job`, `store:runtime`, `search:web`, `integration:vcs`, `integration:issue-tracker`, `integration:design-tool`, `generator:image`, `generator:video`. And `<role>:<parameter>`, where the part after the colon is handed to the provider: `publisher:<platform>` only, whose platform is passed as `--platform` to one implementation that may serve several. An implementation of that form declares the platforms it serves, and the resolver chooses among the implementations that serve the one asked (RS1, in C0.2). As the code stands, `generator` is the first form: the resolver gives its two kinds one folder and a shared fallback variable, but the contract lists them as two fixed classes and no verb receives the kind as an argument.
- **How many skills this touches.** A grep of `requires:` in `skills/*/SKILL.md` finds two bare classes: `mailbox` in `mkt-engage` and `scheduler` in `mkt-publish`; `mailer` and `store` are declared by no skill. After default 57 takes `mailbox` out of `mkt-engage`, one skill declares a bare class. The rename is still done now, because the class table of the orchestrator and the body of both skills name the classes, and a rename after phase E would be a Y change of all three.

Done in C0.2 for everything outside the skill folders; the three skill folders that name a renamed class (`mkt-publish`, `mkt-engage`, `core-orchestrator`'s class table) change in their own rows, after C0.2 has merged, so that each skill is still edited once. The validator's rule that rejects a class without a role is a warning until C0.10 and an error from it, as the contract rules of C0.1 are.

**14b. Four design rules, written into `AGENTS.md`** (A10). They are the part of the SOLID principles that holds for text a model interprets:

1. A skill names no harness (principle 1, already enforced).
2. A skill's procedure names no social platform. It declares the class it needs and reads what is specific to a platform from that platform's reference (decision 14c). What a user types in a request may name a platform.
3. Adding a platform adds a reference file, a data file where a script needs one, and, where something is executed, a provider. It does not edit a skill's procedure, and only that platform's cases are run. The rule has a limit, written into `AGENTS.md` with it (FR-I9): it holds for a platform whose post is text with optional media, the shape of the one platform built today. A platform of another shape (a post that is only an image, a short video) is expected to edit the payload builder of `mkt-publish`, the post template of `mkt-social-copy` and the gate of `mkt-engage`, each a Y or an X change of its skill, tested as the model asks. Two further exceptions, said plainly (PR3): a skill whose script parses a platform's own format carries that parser as code (the comment-link parser of `mkt-engage`, the profile-export parser of `brand-profile`), and adding a platform that needs a new parser edits that script, a Y change of that one skill; and `brand-name`'s table of networks to check is inside that skill, so a row added there is a Y change of it.
4. One skill per job. A skill is split only when the part has its own trigger (someone would ask for it alone), its own requirements or side effects, or its own artifact. Smaller is not a goal: every installed skill costs a line of the listing budget, a flow to compose it and a first full test. No skill is split before phase E.

Not adopted, with the reason: a formal profile contract with declared capabilities, and a validator rule that refuses platform names, wait until a second platform is built, because a contract drawn from one example describes that example. The code host is out of scope: no second host is planned, decision 5 installs its command-line tool in the image so that the branch that uses it is measured, and `ops-repo-baseline` has the host as its subject.

**14c. Platform references, tested per platform** (inventory in `audit-2026-10-02/platform-inventory.md`).

- Where: `shared/references/platforms/<platform>.md`, one file per social platform, read by a skill at `../../shared/references/platforms/<platform>.md`. It holds what the platform is as a medium: text limits, media it requires, how links behave, the shape of a post's URL and of its identifiers, what can be read from outside. What belongs to one implementation (credentials, that service's errors, how to call it) stays in the provider: one provider may serve several platforms, and six of the eight skills that need platform knowledge declare no publisher.
- The step in a skill is literal, and where the platform comes from is defined once, because 14 of the 17 base prompts of the skills that first got the step name no platform (FR-B2). The platform is the `Network:` field of the calendar row or of the post file the step works on, lowercased; when there is none, the platform the task line of the request names; when neither names one, the skill asks. The step then reads "the reference of that platform; if there is no such file, stop and say the platform is not supported". A skill reads only that one file. `brand-name` is exempt: it checks a name on several networks at once, and the `--platform` flag of its `handle_check.py` already names the place a handle is checked on (a code host, a package registry), so that flag keeps its meaning and the script takes no `--platform-file`.
- Scripts take `--platform`. Simple machine data a script needs (URL patterns, host names, length limits, the media types, size and count a post may carry, whether a post needs text) is in `shared/references/platforms/<platform>.json`, beside the reference, and the script reads it through a path given by flag (`--platform-file <path>`; the skill's step passes it), never from a table in the skill and never by a relative path of its own, because a scheduled job runs scripts from a flat folder of copies. So adding a platform does not edit the script. A parser that is code for one platform stays in its skill behind `--platform` (rule 3 of decision 14b). The callers outside the skills follow in the same pull request as the script they call: `scripts/runtime.py` runs `parse_notification.py`; `scripts/runtime_vote.py` and `scripts/vote_job.py` run `vote_update.py`; `scripts/runtime_vote.py` runs `payload.py`, and the snapshot it hands the scheduler carries the platform's data file under its own name (PR3).
- Scope now: the first reference (the one platform built today) and the eight skills that carry its knowledge (`brand-identity`, `brand-name`, `brand-profile`, `brand-strategy`, `mkt-engage`, `mkt-publish`, `mkt-social-copy`, `mkt-vote-round`). The platform inventory lists seven; `mkt-social-copy` is the eighth, because its procedure carries the platform's rules on hashtags and on a link in the first comment (FR-I9). The first data file holds every limit the runtime holds as a constant today, so that no later item edits it (FR-I5, C0.9). `brand-name`'s list of networks to check stays a table inside that skill. References for other platforms are written when each has a real task, never from general knowledge.
- Measurement (PR2):
  - The cases of a platform live in `skills/<name>/evals/platforms/<platform>.json`, with their fixtures under `skills/<name>/evals/platforms/<platform>/files/`. All of `evals/` is outside the skill's content hash, since the adapters remove it from the copy a model sees. Adding a platform's cases therefore changes no version and no evidence of the skill.
  - The gate and the pessimistic score are computed on the cases of `evals/evals.json` only: a platform whose cases fail changes no band. The cases the eight skills have today stay in `evals/evals.json` and are the base, except the one `mkt-publish` case that moves (row 46).
  - `eval_run.py --platform <name>` runs that platform's case file, with the skill only, and writes one evidence file whose run lines carry `platform` (B7a). It is a partial test: nothing is refused, and it needs no base result to exist. The status shows, per platform, the mean and the number of runs of those lines, and no score.
  - No shared reference is in the measurement fingerprint (default 21). A run line names, in `context_sha256`, the references staged into the run, a platform's reference and data file included. When the first platform's reference is edited, the lines that ran with the old one become inherited evidence: the skills whose cases read it are `watch` until they have lab runs with the new one, and nothing else moves.
  - The pilot of phase D makes one real full test and then exercises the `--platform` path (D3); phase E runs each skill's platform cases after its full test.

- Installations get `shared/references/` beside the skills in A6 (PR4); in evals it is staged by the runner (B2).

#### The rule for case changes

- An assertion changes only for a stated reason: it never influences the score (it passes in every run of every variant and is a language assertion or content any model produces); it fails a good output for a formality; it rests on something the grader cannot see; it is conditional; or it contradicts the skill. When the output is not good, the skill is fixed, never the assertion.
- A guard (something that must not happen, or a question that must be asked first) is kept even when it always passes, is reworded so that the grader can verify it, and carries its tag: `guard`, or `guard:<effect>` when it guards a declared side effect (C0.7). Where the case can reach the gate, the guard of a side effect is the assertion that the reply asks before the effect, which a run without the skill fails, and not only the assertion that nothing happened, which every variant passes (MB1).
- A content assertion that always passes is replaced by a sharper one that the audit's evidence shows the baseline failing. Of two candidates, the one that is not a format assertion is taken: an assertion on a form only the skill defines fails every baseline, so it can never show a skill that makes a strong model worse (default 92). A replacement that still passes everywhere in the full test of phase E is listed in that phase's report and left alone until the skill is next changed.
- **Every assertion change is listed before and after in the pull request**, with its reason; so is every change to a prompt, an expected output or a fixture.
- A new case follows C0.7 and is listed with the behaviour it measures.
- After phase C a case changes under the same rule, in the repair loop of phase E or later. A changed case has a new hash: its evidence drops, its baseline expires, and it enters the gate through a full test of the skill, every case with the skill, the baseline run for that case and reused for the others (about 13 runs on the reference model for an average skill). It is never run alone into the gate, however often it is edited: an edit followed by a run of that one case would discard its poor runs each time (P5). An added case is `pending`, changes no band, and runs with `--cases <id> --baseline` (6 runs). A deleted case, and a case deleted and written again under another id, are listed with their reason.

**A skill that fails.** Nothing is held open for it, and the loop has no cap on repairs: what limits it is that the gate cannot be moved by choosing what to run again.

1. An incomplete event (infrastructure, or a pause on the account limit that was not resumed) is resumed with `--resume` and writes nothing until it is complete. A full test that is abandoned instead is closed with `--close`: its file is written as an incomplete `full` event and its lines stay in the gate of that version, so that giving up a test that is going badly and starting another is not a second draw (B12; P3). The resumptions of one run have a cap (`max_resumes`, B5): a run that is still incomplete after it is written as a line with `outcome: timeout` and score 0, with the skill and without it alike, so that a run that always times out or is always refused cannot hold an event open for ever, and dropping it cannot raise a mean (FR-I14, MI11).
2. A full test that fails the gate, or that passes it while a guard assertion has a confirmed failure, is read: the failed gradings, the replies, and for the floor tier the transcript. Each failure is classified as a skill defect, a case defect, or the instrument.
3. A defect of the instrument is fixed as the kind of change it is (B10). Infrastructure: nothing else happens. Execution side: an epoch for the skills it affects, which run their cases again with the skill. Grader side: the floor is raised, and every skill tested so far is tested again in full. 4. A skill defect is fixed in the skill: a Y or an X change, with its bump. It is never run alone into the gate, the first time or any later time (P5).
